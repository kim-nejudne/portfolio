## Concept

Reading a property by name is everyday JavaScript: `obj[key]`. With the key typed `string`, it doesn't compile, which is the error <Lesson id="m04-objects/03-index-signatures-and-record" /> met with keys from `Object.keys`:

```ts run errors
type Track = { title: string; artist: string; seconds: number };

function field(track: Track, key: string) {
  return track[key];
}
```

`Element implicitly has an 'any' type because expression of type 'string' can't be used to index type 'Track'.`, then `No index signature with a parameter of type 'string' was found on type 'Track'.` A `Track` has three properties, and most strings name none of them. Only a type with a `string` index signature can be read with any string.

The key should be one of `Track`'s property names, and `keyof Track` is that type: the union `'title' | 'artist' | 'seconds'`. (<Lesson id="m06-type-operators/01-keyof-typeof-indexed-access" /> takes `keyof` further.) With `key: keyof Track`, `field` compiles, but its result is `string | number`, the type of every property at once, because the signature doesn't say which key came in. The link between the key and the result is a type parameter (5.1), constrained to the keys (5.2):

```ts twoslash
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const track = { title: 'Intro', artist: 'The xx', seconds: 128 };

const title = get(track, 'title');
//    ^?
const seconds = get(track, 'seconds');
//    ^?
```

Read the signature from left to right. `T` is inferred from `obj`. `K extends keyof T` says that `K` is one of `T`'s property names, and it is inferred from `key` as the literal type of the name, such as `'seconds'`. `T[K]` is an indexed access type: the type of the property `K` of `T`, so `number` for `'seconds'`. Inside the body, `obj[key]` compiles because `key` is a key of `obj`, and its type is `T[K]`. Outside, a name `T` doesn't have is rejected at the call: `get(track, 'album')` reports `Argument of type '"album"' is not assignable to parameter of type '"title" | "artist" | "seconds"'.`

Like every type, all of this is erased. The JavaScript is `function get(obj, key) { return obj[key]; }`.

## Examples

**A union of keys.** `K` is whatever the key's type is. When that is a union of names, `T[K]` is the union of those properties' types, no more:

```ts twoslash
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

type Track = { title: string; artist: string; seconds: number };
const track: Track = { title: 'Intro', artist: 'The xx', seconds: 128 };

const sortKey = track.seconds > 60 ? 'seconds' : 'title';
const value = get(track, sortKey);
//    ^?
```

`sortKey` is a `const`, so its type is `'seconds' | 'title'`, and `value` is a `string | number`. It can't be a `boolean` or anything else: the result is exactly as precise as the key.

**`pluck`: one property of every item.** The key constraint works the same when `T` is the item type of a list, and `T[K]` can sit inside another type, here an array:

```ts run
function pluck<T, K extends keyof T>(items: readonly T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}

type Track = { title: string; artist: string; seconds: number };
const album: Track[] = [
  { title: 'Intro', artist: 'The xx', seconds: 128 },
  { title: 'VCR', artist: 'The xx', seconds: 157 },
];

const titles = pluck(album, 'title');
const lengths = pluck(album, 'seconds');
console.log(titles.join(', '), Math.max(...lengths));
```

`titles` is a `string[]` and `lengths` a `number[]`, so `Math.max(...lengths)` compiles and `Math.max(...titles)` would not.

**`setProperty`: the value must fit the key.** `T[K]` works as a parameter type too. The compiler checks the value against the property the key names:

```ts run
function setProperty<T, K extends keyof T>(obj: T, key: K, value: T[K]): void {
  obj[key] = value;
}

type Track = { title: string; artist: string; seconds: number };
const track: Track = { title: 'Intro', artist: 'The xx', seconds: 128 };

setProperty(track, 'seconds', 130);
setProperty(track, 'title', 'Intro (live)');
console.log(track);
```

`setProperty(track, 'seconds', '130')` reports `Argument of type 'string' is not assignable to parameter of type 'number'.` The check is only as precise as `K`, though. With the `sortKey` from above, `value` must be a `string | number`, so `setProperty(track, sortKey, 'long')` compiles, and it writes a string into `seconds` when `sortKey` is `'seconds'`. Pass a single name when you write.

**When the result doesn't depend on the key.** A `sortBy` takes a property name too, but it returns the items, whichever key it sorted by. Then `key: keyof T` is all it needs, with no `K`:

```ts run
function sortBy<T>(items: readonly T[], key: keyof T): T[] {
  return [...items].sort((a, b) =>
    a[key] < b[key] ? -1 : a[key] > b[key] ? 1 : 0,
  );
}

type Track = { title: string; artist: string; seconds: number };
const album: Track[] = [
  { title: 'VCR', artist: 'The xx', seconds: 157 },
  { title: 'Intro', artist: 'The xx', seconds: 128 },
];

console.log(sortBy(album, 'title').map((track) => track.title));
console.log(sortBy(album, 'seconds').map((track) => track.seconds));
```

`sortBy(album, 'year')` is still rejected. A `K` earns its place when it appears a second time, in `T[K]`, as it did in `get`, `pluck` and `setProperty`. <Lesson id="m05-generics/05-when-generics-hurt" /> comes back to type parameters that appear only once.

## Pitfalls

**Typing the key as `keyof T` when the result depends on it.** Without its own type parameter, the key can be any of the names, so the result is the type of any of the properties:

```ts run errors
function get<T>(obj: T, key: keyof T): T[keyof T] {
  return obj[key];
}

type Track = { title: string; artist: string; seconds: number };
const track: Track = { title: 'Intro', artist: 'The xx', seconds: 128 };

const title: string = get(track, 'title');
```

`Type 'string | number' is not assignable to type 'string'.`, then `Type 'number' is not assignable to type 'string'.` The call knows the key is `'title'`, but the signature has nowhere to keep that. Give the key a type parameter, `K extends keyof T`, and return `T[K]`.

**Passing a key that is only known to be a `string`.** The constraint checks the key's type, not its value. A `let` widens `'title'` to `string` (<Lesson id="m01-types/02-primitives-literals-widening" />), and a `string` is not a key of `Track`:

```ts run errors
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

type Track = { title: string; artist: string; seconds: number };
const track: Track = { title: 'Intro', artist: 'The xx', seconds: 128 };

let key = 'title';
console.log(get(track, key));
```

`Argument of type 'string' is not assignable to parameter of type 'keyof Track'.` The same goes for a key from `Object.keys`, which is a `string` (4.3). Declare the key with `const`, or type it `keyof Track`, or loop over a list of names declared `as const`: `for (const key of ['title', 'artist'] as const)` gives each key its literal type.

**Treating `K` as a string.** `keyof T` is not always a union of strings. Property names can be numbers and symbols too, and for a `T` with a `string` index signature `keyof T` is `string | number` (6.1). Inside a generic, `K` could be any of them:

```ts run errors
function label<T, K extends keyof T>(obj: T, key: K): string {
  return `${key.toUpperCase()}: ${obj[key]}`;
}
```

`Property 'toUpperCase' does not exist on type 'string | number | symbol'.` When only string names make sense, say so in the constraint, `K extends keyof T & string`, and the body may use string methods. Or turn the key into a string first, with `String(key)`.
